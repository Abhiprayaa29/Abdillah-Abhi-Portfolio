- **Anonymous visitor tracking** (first-party, no third-party analytics): `script.js` mints a UUID v4, stores it in `localStorage.abhi_vid` **and** in a first-party `abhi_vid` cookie, and POSTs it to `/api/visit` after `load`. Pages Functions in `functions/api/visit.js` and `functions/api/stats.js` persist it to Cloudflare D1 (`schema.sql`, single `visitors` table: `visitor_id`, `first_seen`, `last_seen`, `visit_count`). Counting rules: a new id inserts a row and returns `isNew:true` (+1 unique); the same id inside a **60-second dedupe window** returns `duplicate:true` and changes nothing, so a refresh, a double-fired request, or a retry can never inflate the counters; the same id after the window returns `isNew:false, duplicate:false` and increments `visit_count` only, so unique stays put while `totalVisits`/`returningVisits` rise. The id is validated against `^[0-9a-f]{8}-…-…-…-…{12}$` before it touches SQL (a `1; DROP TABLE visitors;` shaped id is rejected with 400), requests are parameterised, and the response carries no IP address, user agent, referrer or identity field. Until a D1 binding exists both endpoints answer `HTTP 200 {"ok":false,"available":false}` - the route is healthy, only the counter is off - so the browser logs no failed request and the site behaves exactly as before. (A 5xx was deliberately avoided: Lighthouse's `errors-in-console` audit drops best-practices to 96 when `Failed to load resource: 503` appears in the console.) Verified by two suites: **`visit-test.js` 26/26** (first visit, five refreshes, six *concurrent* duplicates, second visitor, four invalid ids, cookie-only and GET variants, stats agreement, on-disk row shape, privacy key scan, then a second server with `DEDUPE_MS=0` to cross the window and prove a genuine returning visit bumps `totalVisits`/`returningVisits` while `uniqueVisitors` stays fixed) and **`cdp-visit.js` 26/26** in real Chromium (localStorage + cookie written and equal, three reloads leaving unique at 1 and total at 1, a simulated later session producing `isNew:false` with unique still 1 and returning 1, a double POST keeping both totals fixed, a second device id counting as a new visitor, `.nav-wrap` still 52 px / `.site-header` still 53 px, five project rows and seven sections intact, zero JS errors). Measured cost, baseline vs. tracking (identical machine, identical Lighthouse throttling, three runs each): **light 97/97/96 -> 96/96/96**, **dark 95/95/96 -> 97/97/97**, `best-practices` 100 in all twelve runs - i.e. no measurable performance cost from the post-`load` request. Against the live origin the same code scores anywhere from 59 to 100 depending on the run (FCP swings between 1.2 s and 6.4 s), so production numbers here are network-dominated; the light/dark pairs above isolate the code. Production recruiter scan after deploy: **22/22**, with `No console/page errors ([])`. The D1 binding itself is a manual dashboard step; steps are in `README.md`.
